
# KNOT SO FAST — 해커톤 재현 키트
해상 물류 최적화 플랫폼을 하루 만에 다시 만들기 위한 명세 묶음입니다. 소스 코드 없이 이 문서들만으로 원본과 거의 동일한 앱을 재현합니다.

이 문서를 먼저 읽고, 그다음 각자 담당 스펙으로 갑니다. 5분이면 충분합니다.



## 1. 반입 번들 확인
ksf-kit/
├── specs/                   ← 문서 20개 (지금 읽고 있는 것)
└── project-files/           ← 프로젝트에 복사할 파일들
    ├── src/mocks/           샘플 데이터
    ├── public/              이미지·폰트
    └── scripts/             항로 생성 스크립트

project-files/가 있으면 Track A, 없으면 Track B입니다.


|  | Track A | Track B |
| --- | --- | --- |
| 샘플 데이터 | 복사만 하면 끝 | 스펙의 표를 보고 작성 (30~60분) |
| 항로·이미지·폰트 | 그대로 사용 | 폴백 사용 (스펙에 명시됨) |


Track B여도 기능은 전부 완결됩니다. 지도 항로가 직선으로 보이는 정도의 차이입니다.



## 2. 프로젝트 구조와 배치
knot-so-fast/            ← 당일 새로 만들 프로젝트
├── docs/specs/          ← specs/ 를 여기로 복사
├── src/
│   ├── app/             화면
│   ├── features/        화면별 컴포넌트
│   ├── shared/          공용 컴포넌트·타입·유틸
│   └── mocks/           ← project-files에서 복사
├── public/              ← 〃
└── scripts/             ← 〃

ksf-kit/ 은 프로젝트 안이 아니라 옆에 둡니다.

작업폴더/
├── ksf-kit/            ← 반입 번들
└── knot-so-fast/       ← ①에서 생성할 프로젝트

프로젝트를 만드는 시점에는 프로젝트가 아직 없으므로 명세를 ksf-kit/specs/ 에서 읽어야 하고, 프로젝트 안에 두면 src/mocks 와 public 이 5MB 중복되며 tsconfig 가 사본까지 타입 검사합니다.

복사는 두 번, 시점이 다릅니다.

# ① 프로젝트 생성 직후 — 명세를 먼저 들여온다
New-Item -ItemType Directory -Force docs | Out-Null
Copy-Item -Recurse -Force ..\ksf-kit\specs docs\

# ③ 타입·상수를 만든 뒤 — 샘플 데이터와 자산
Copy-Item -Recurse -Force ..\ksf-kit\project-files\* .

# ① 프로젝트 생성 직후
mkdir -p docs && cp -r ../ksf-kit/specs docs/

# ③ 타입·상수를 만든 뒤
cp -r ../ksf-kit/project-files/* .

왜 나눠서 하는가

명세(specs/)는 가장 먼저 필요합니다. ①부터 LLM이 읽어야 합니다.
데이터(project-files/)는 타입·상수 뒤에 옵니다. src/mocks/*.ts 가 @/shared/types 를 import하므로, 먼저 복사하면 타입 에러가 쏟아져 진짜 오류를 가립니다.

순서: 프로젝트 생성 → specs 복사 → 타입·상수 → project-files 복사 → 나머지 셸

문서를 프로젝트 안에 두는 이유: 에디터에서 바로 열리고, LLM에게 docs/specs/VESSEL.md 보고 만들어줘처럼 경로로 지시할 수 있습니다.



## 3. 당일 작업 순서

### 0단계 — 전원 (10분)
이 README를 읽고 Track A/B를 확인한 뒤, 아래 담당을 정합니다.

### 1단계 — 한 사람이 단독 (60~90분)
BOOTSTRAP.md 를 처음부터 끝까지 실행합니다. 이게 끝나야 나머지가 시작할 수 있습니다.

아래 순서를 지키세요. ③ 복사를 ②보다 먼저 하면 타입 에러가 쏟아집니다.

BOOTSTRAP_PROMPTS.md 에 아래 5단계가 그대로 복사해 쓸 수 있는 프롬프트로 준비되어 있습니다. 위에서부터 순서대로 실행하면 됩니다.


|  | 할 일 | 참조 |
| --- | --- | --- |
| ① | 프로젝트 생성 + 명세 반입 — create-next-app + 설정 4종 → specs/ 를 docs/specs/ 로 | BOOTSTRAP.md 2~3장 · 2장 |
| ② | 타입·상수 작성 — src/shared/types/, src/shared/constants.ts | BOOTSTRAP.md 4장 |
| ③ | 샘플 데이터·자산 복사 — project-files/* → 프로젝트 루트 | 2장 |
| ④ | 전역 스타일 — globals.css + 디자인 토큰 + 다크 모드 변형 | BOOTSTRAP.md 5장 |
| ⑤ | 앱 셸 — 레이아웃·Provider·Context 3종·공통 컴포넌트 | BOOTSTRAP.md 6~8장 |


③이 ②보다 뒤에 오는 이유: src/mocks/*.ts 가 @/shared/types 와 @/shared/constants 를 import하기 때문입니다. 먼저 복사해도 파일은 멀쩡하고 타입 에러만 뜨다가 ②에서 해소되지만, 빨간 줄을 보며 작업하면 진짜 오류를 놓치기 쉽습니다.

Track B(번들에 project-files/ 가 없음)라면 ③ 대신 각 스펙의 "재현용 샘플 데이터" 표를 보고 src/mocks/*.ts 를 직접 작성합니다(30~60분).

완료 기준: 로그인해서 빈 페이지가 사이드바와 함께 뜨는 상태 (BOOTSTRAP.md 10장의 검증 9항목 통과)

### 2단계 — 전원 병렬
각자 담당 화면 스펙 하나를 들고 src/app/(main)/{경로}/page.tsx부터 만듭니다.

|  | CARBON.md | 약 690줄 | ★★ · 프롬프트 |
|  | VESSEL.md | 약 790줄 | ★ · 프롬프트 |

### 3단계 — 통합·리허설
화면을 합치고 데모 시나리오를 두 번 돌려봅니다.



## 4. 시간이 부족할 때 자르는 순서
앞에서부터 잘라냅니다. 각 스펙에 "이건 없어도 동작한다"가 표시되어 있습니다.

ADMIN_USERS.md — 사이드바에서 메뉴만 빼면 됨
SIMULATION.md의 PDF 내보내기
DASHBOARD.md의 L3·L4 (리스트 패널, 실시간 API, 딥링크)
외부 API 연동 전부 (기상·태풍·Gemini) — mock으로 대체

로그인·대시보드·자기 담당 화면 1개만 있어도 데모는 성립합니다.



## 5. 막혔을 때
KNOWN_PITFALLS.md를 먼저 봅니다. 원본 개발 중 실제로 시간을 잃었던 함정 38건이 증상별로 정리되어 있습니다.


| 증상 | 예시 |
| --- | --- |
| Hydration failed | 1.1 |
| 필터가 간헐적으로 안 먹음 | 1.3 |
| 지도 타일에 Zoom Level not supported | 2.5 |
| 목록과 팝업의 시각이 다름 | 3.1 |
| 카운트업 중 레이아웃 흔들림 | 4.1 |


0장의 증상 인덱스에서 검색하세요. 처음부터 읽을 필요는 없습니다.



## 6. 문서 지도

| 문서 | 언제 읽나 |
| --- | --- |
| README.md | 지금 (전원) |
| BOOTSTRAP_PROMPTS.md | 1단계 실행용 프롬프트 — BOOTSTRAP.md와 함께 |
| 화면별 *_PROMPTS.md | 2단계에서 자기 담당 화면 것만 |
| BOOTSTRAP.md | 1단계 담당자가 처음부터 끝까지 |
| KNOWN_PITFALLS.md | 막혔을 때 증상으로 검색 |
| 화면 스펙 8종 | 2단계에서 각자 담당분만 |


모든 스펙은 같은 구조입니다 — 개요 → 데이터 모델 → 화면 구성 → 계산 로직 → 다국어 사전 → 색상 토큰 → 엣지 케이스 → 재구현 체크리스트.

구현 전에 엣지 케이스 장을 먼저 훑어보세요. 놓치기 쉬운 것만 모아둔 장이라, 나중에 디버깅할 시간을 아껴줍니다. 다 만든 뒤에는 체크리스트로 누락을 확인합니다.



## 7. 기억할 원칙 3가지
① 데이터는 mock으로 간다. DB·백엔드를 붙일지 고민하지 마세요. 나중에 올리는 경로가 BOOTSTRAP.md 9.4장에 있습니다.

② 계산 로직은 한 곳에만 둔다. 같은 지표를 화면마다 따로 계산하면 숫자가 어긋납니다. 원본에서 이걸로 전 화면을 재작업한 적이 있습니다.

③ 스펙의 샘플 데이터를 그대로 씁니다. 값 하나하나가 화면의 특정 상태를 보여주도록 설계되어 있습니다(지연 항차, 정비 중 선박, 비활성 사용자 등).



## 8. 번들 갱신 (해커톤 전, 준비 담당자만)
이 키트는 원본 저장소에서 자동 조립됩니다. 수동으로 파일을 복사하지 마세요.

### 순서를 반드시 지킬 것
스펙 수정  →  빌드  →  반출
                ↑
        항상 가장 마지막

### ⚠ 빌드는 스펙을 다 고친 뒤 마지막에 돌립니다
문서를 수정하고 빌드를 다시 돌리지 않으면 구버전 스펙을 들고 가게 됩니다. 이 방식의 유일한 실패 지점이며, 당일 현장에서는 알아채기 어렵습니다.

스펙을 한 글자라도 고쳤다면 → 다시 빌드하세요.

# 원본 저장소 루트에서
node scripts/build-kit.mjs

ksf-kit/
├── README.txt        ← 빌드 시각이 기록됨 (현장에서 신선도 확인용)
├── specs/            ← docs/specs/*.md
└── project-files/
    ├── src/mocks/    ← apps/web/src/mocks/*
    ├── public/       ← apps/web/public/{fonts,images}
    └── scripts/      ← scripts/*.py

### 출발 전 체크리스트
스펙 수정을 전부 마쳤다
그다음 node scripts/build-kit.mjs 를 실행했다
출력이 총 41개 파일 · 7.1MB, specs 20개 인지 확인했다
ksf-kit/README.txt 의 빌드 시각이 방금인지 확인했다
번들을 실제로 반출했다 (USB · 클라우드 · 개인 저장소)

ksf-kit/은 .gitignore 대상이라 git push로는 나가지 않습니다. 7.1MB이니 압축해서 별도로 옮기세요. 이 단계를 빠뜨리면 현장에서 번들이 아예 없습니다.

### 그 밖에
원본 폴더가 하나라도 없으면 경고 후 실패하므로, 번들이 조용히 불완전해지지 않습니다.
빌드는 매번 ksf-kit/을 지우고 다시 만듭니다. 파일명을 바꿔도 구 파일이 남지 않습니다.

당일에는 이 스크립트가 필요 없습니다. 번들만 있으면 됩니다.

### 권장 — 출발 전 리허설 1회 (30분)

프롬프트가 의도대로 동작하는지 확인됩니다.
